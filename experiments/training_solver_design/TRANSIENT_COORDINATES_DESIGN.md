# 短期共有/相对坐标与可审计的状态回迁

后续结果见 TRANSIENT_RESULTS.md：40 条真实分支完成，未建立稳定终局
优势，不推进当前配置。下面保留提出假设时的设计与后续工程选项。

2026-09-26。候选设计，尚无 GPU 收益验证，也没有新颖性结论。
该设计来自 room 的开发结果，不能把后续同场景测试当独立确认。

## 1. 由现有证据收窄问题

room 中永久使用 pair_full 在 32 步 A/B 平均改善，B 三组均超过原生
重放差；128/256 步优势消失。单纯保留新坐标更久没有得到更好结果。
这提示一个待验证的问题：新坐标是否只适合分裂后的短暂适应期？
不据此声称 32 步是最优窗口、所有场景都成立或永久方案一定失败。

最小下一项对照固定在 32 步回迁，避免在同一批数据上穷举寿命后
只报告最佳窗口。32 来源于已观察的开发窗口，属于事后提出的假设。
保持所有候选、分裂初始化、相机序列与训练预算不变。

## 2. 不同偏差修正年龄下，如何给回迁明确语义

明确约定：分裂前，相对梯度历史全为零；共有梯度历史就是父体历史。
两个模式的原始 EMA 都使用相同 beta1/beta2、每次 dense 更新一起递推。
相对模式在产生参数更新时可用 fresh bias clock；它不改变原始 EMA
的递推式。因此，即使更新使用不同的偏差修正年龄，以下原始矩关系
仍有明确解释，前提是上述零延伸历史约定，而非任意混合的 EMA 权重：

```text
g_plus  = (g_shared + g_relative)/2
g_minus = (g_shared - g_relative)/2

c <- beta2*c + (1-beta2)*g_shared*g_relative, c_birth=0
m_plus/minus = (m_shared +/- m_relative)/2
v_plus/minus = (v_shared + v_relative +/- 2*c)/4
```

由线性 EMA 递推逐步归纳可得：这恰好等于沿已发生的轨迹记录
物理子体梯度的 EMA，出生前各子体继承 m_parent/2、v_parent/4。
“沿相同轨迹的梯度历史”不等于“独立物理 Adam 会产生相同轨迹”。

回迁后的 physical Adam 统一使用旧组时钟。此约定保持原始梯度历史，
**不保持下一次更新步幅，也不保持 fresh-relative 的偏差修正效果**。
这里的切换本身仍是优化策略改变，必须验证切换后的短期冲击及终局。
不能把原始矩的代数正确性称为等价加速或有效步长连续。

## 3. 最小完整训练契约

1. 每次拓扑改变前，把现存配对全部回迁，再执行原有 split/prune。
2. 新 split 配对只存活 32 次更新；共有模式继承父体原始矩，相对矩
   和交叉矩从零开始。只保留当前活动配对，没有持久分裂树。
3. 每次 backward 后、Adam 更新前更新交叉矩。参数更新结束、清空梯度
   后才回迁。回迁先 decode 原始参数，再恢复常规 exp/sigmoid/normalize。
4. 回迁保留存活行和所有组时钟。交叉矩在回迁后释放；后续物理 Adam
   正常更新。若新拓扑事件提前到来，提前回迁，不跨拓扑保留失效配对。
5. 初版要求 dense 同步计数、同一 beta、二子体 split；稀疏异步计数、
   多子体 split 或优化器特有状态不属于此初版契约。

这给重复分裂/剪枝提供了一个可实现的方案，仍未与完整训练器集成。
不是已经证明性能的系统。额外存储是每个活动配对每个标量一个交叉矩；
统计回迁、解码与交叉矩的实际访存时间，不按零开销估计。

## 4. 最小验证与拒绝条件

CPU 对照把共享/相对 raw EMA 回迁到物理 EMA，再与两个物理子体沿同一
梯度轨迹独立累计的 PyTorch Adam 状态比较；其中相对参数确实使用 fresh
更新时钟。另验证无交叉矩时无法恢复物理二阶矩的反例。

下一步 GPU 对照：native+repeat、永久 pair_full、32 步回迁 pair_full、
物理 .5/.25 和 .2/.04 继承；若有优势，再添加清零式回迁以分离历史作用。
先复核回迁前后图像完全一致，记录回迁后 1/8/32 步、终局 A/B 与时间。
两场景是开发数据，不作正式未见视角或统计显著性结论。

若优势仅在观察窗口内出现，回迁后仍不能保留，停止这一具体策略。
即使保留，也只说明局部机会；随后才值得做完整训练、官方新视角测试和
FastGS/BOGausS 等强实现的同预算比较。整体目标仍是时间—质量优势，
不是把短暂 loss 改善当作更快、更高质量的完整 3DGS。

## 5. 有机会后才做的 O(KD) 实现

本次 room/garden 各有 260530/1841621 个高斯，但只编辑 256 个父体。
Python 代理每次复制全部原始参数的 O(ND) 成本远大于活动配对规模。
不能由这 256 个父体的微小收益外推整场景大幅加速。

更小的实现可以始终保存物理 θ_plus/minus 供渲染，仅在优化器处理
活动配对：g_shared=g_plus+g_minus、g_relative=g_plus-g_minus，更新
mode EMA 得到两种增量，然后令 Δθ_plus=Δshared+Δrelative、
Δθ_minus=Δshared-Δrelative。这样无需在每次前向复制整个场景，额外
工作随 K 而非 N 增长；回迁时只需转换 mode EMA，参数已经是物理形式。

这是尚未实现/计时的工程方案。物理参数逐步累加与持久 μ/δ 再 decode
在 FP32 下可能有不同舍入轨迹，必须先用 FP64 参考与真实图像比较，
不能宣称逐位等价。若当前机制不能通过收益检查，先不写生产 kernel。
