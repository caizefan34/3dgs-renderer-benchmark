# Vol3DGS 体透射率的稳定射线坐标：代数与机会门

2026-09-27。用户要求完整训练更快、正式未见视角更好，且不能以低分辨率主训练换速度。本页只核查一个**可能加速已有高质量体透射率表示**的低层计算，不把已发表的解析积分或这里的配方称为原创方法。没有真实 CUDA 训练器、完整成本或重建质量结果。

## 固定版本来源和待解瓶颈

[Vol3DGS](https://arxiv.org/abs/2412.03378) §4 已在 rasterizer 内解析积分 3D Gaussian 沿射线的透射率；附录 F 作者报告其 30K Mip-NeRF 360 训练比同实现 3DGS 慢（61min 对 51.5min）。其公开仓库 `Vol3DGS` 的 `main` tree `dd175d52938264770a783cbb7929e20572675544` 指向 Slang 子模块提交 `5eca1185550c35e3236c511c311aee3eb9129169`。本地快照 `topology_sources/vol3dgs_{utils,vertex_shader,alphablend_volr_shader}.slang` 的 hash 见 `sources.json`。

固定代码先在像素处将射线 `d` 归一化，再由 `evaluate_splat_volr` 对每个高斯–像素计算 `a=dᵀAd`、`b=μᵀAd`、`t=b/max(ε,a)`、残差 `r=td−μ`、`power=−rᵀAr/2`、`sigma_d=1/sqrt(max(ε,a)+ε)`，用两次指数形成 `alpha=min(.99,1−exp(−2.506 κ sigma_d exp(power)))`，其中 `ε=1e−7`；`A=Σ⁻¹` 已由 vertex shader 计算/储存。这解释了论文所述每像素额外算术，但**不能仅凭公式推出当前编译器的指令数或可节省的墙钟**。此代码忽略射线积分的近端尾部，且对 `b≤0` 返回零；候选实现须匹配固定源码语义，而不能把不同体渲染公式冒充 parity。

## 稳定的中心射线恒等式

令相机坐标高斯中心为 `μ`，`μ_z>0`，**单位长度**像素射线为 `d=normalize(u,v,1)`，中心射线 `d₀=μ/‖μ‖`，`e=‖μ‖(d−d₀)`，`A=Σ⁻¹`。把射线参数写成 `t=‖μ‖+s`，则 `td−μ=e+s d`。对 `s` 完成平方：

```text
a = dᵀ A d
k = dᵀ A e
s* = −k/a
t* = ‖μ‖−k/a
q_min = eᵀ A e − k²/a
power = −q_min/2,  仅在 t*>0 时与固定源码的峰值分支对应
```

它与 `c−b²/a`（`c=μᵀAμ`，`b=dᵀAμ`）在实数代数中相同，但用离中心射线的小偏移 `e` 避免深度/尺度比很大时两项巨大数相减。公式本身只是配平方，不是原创贡献。能否预计算局部二次型系数、减少每像素矩阵运算和属性读取，且保留 FP32 梯度/光栅语义，**尚未实现或测量**。直接 `c−b²/a` 不能作为安全的性能捷径。

## 2 万组合成 FP32 筛查

`volumetric_local_ray_oracle.py` 固定种子 20260927，采样旋转 SPD 协方差、深度 `[1,50]`、三轴尺度 `[.001,.1]`、中心光学深度 `[.1,5]`，像素射线偏移约一最小尺度/深度，并按固定 shader 将其归一化；用 FP64 原残差形式作参考，比较三种 FP32 算法。合成 alpha 使用固定 shader 的 `2.506` 系数、`1e−7` 分母 ε 与 `.99` 上限，但 NumPy 运算并不等价于 Slang GPU 指令或自动微分。输入分布是**合成**的，不代表 room/garden 实测参数或 GPU 编译结果。

## 2026-09-27 补筛：精确屏幕二次式没有稳定 GPU 前向优势

将未归一化像素射线写成 `w=(u,v,1)`，中心 `μ=z w₀`，`δ=(u−w₀ₓ,v−w₀ᵧ)`，`A=Σ⁻¹` 对称正定。设 `a₀=w₀ᵀAw₀`、`v=(Aw₀)ₓᵧ` 和 `B=z²(a₀ Aₓᵧ,ₓᵧ−vvᵀ)`，则沿射线最小二次型精确为

```text
q_min = δᵀBδ / (wᵀAw)
```

推导：令三维残差 `e=z(w−w₀)`，最小二次型为 `eᵀAe−(wᵀAe)²/(wᵀAw)`；展开后与 `δ` 的三次、四次项相消，剩下上述二次式。`B` 可在每高斯阶段预计算；像素处仍须计算 `wᵀAw`、`μᵀAw` 的前向分支和宽度因子。公式只是经典 Gram 行列式/Schur 补的重写，**不声明原创**；实际 shader 的 `max(ε,a)` 分支须另作逐项 parity。

`volumetric_projective_conic_screen.py/json` 的 20,000 组合成检查中，FP64 power 恒等误差最大 `6.62e−12`；FP32 alpha 相对 FP64 的 p99 绝对误差原残差 `6.66e−5`、预计算 Schur 二次式 `5.17e−5`，两者均未出现负最小二次型。`volumetric_projective_vjp_screen.py/json` 在 4,096 组对称矩阵参数流形上，FP64 逐样本 alpha/VJP 接近机器精度；FP32 两式的中心位置梯度相对范数差 p99 `0.00289`、最大 `0.0622`，尚未与固定 Slang 自动微分/参数梯度对齐。合成 oracle 仅约束这个输入分布。

`volumetric_projective_triton_probe.py/json` 用 RTX 5070 Laptop 的独立**前向算术核**，4,096 个高斯、每高斯 16/64/256 个合成像素，采用配对 CUDA graph 计时。两次进程运行的候选/原核配对中位时间比依次为 `1.048/0.983`、`1.066/0.898`、`0.971/1.084`；比值在 1 两侧波动，**没有稳定加速证据**。每高斯二次式预计算单独约 `0.0011–0.0015 ms`，没有计入上述比值；更未计排序、alpha 合成、原 shader 前后向、完整训练或画质。独立核甚至不能代表真实高斯像素数分布。

**裁决更新：**此项目可保留精确重参数化作为数值参考，但不在当前证据下写生产 Vol3DGS shader 或启动 30K 训练。若重启，先需固定代码的真实 GPU 前向/VJP 与像素分布、全图/完整步成本证明足够大的稳定收益，并解决 FP32 参数梯度差异；再谈质量机制与最新强基线同协议对照。三个脚本及三个 JSON 的 SHA256 分别见文件自身哈希或命令重算；JSON 是本次结果，不是正式基准。
