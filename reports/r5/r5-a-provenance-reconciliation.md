# R5-A: Provenance Reconciliation — R4 Seed-0 Metrics Discrepancy

## Summary

The R4 seed-0 candidate_c `training_metrics.json` for train and truck was **overwritten by an unidentified re-run** at 2026-09-19 01:04–01:07 CST. The original run's metrics survive only in `final_results.json` (mtime 2026-09-18 23:58:04). The R5-A0 audit verified `provenance.json` (from the original run, NOT overwritten) and `camera_sequence.npy` (also NOT overwritten), so the audit's conclusion `ORIGINAL_R4_PAIR_REUSABLE=YES` was correct for provenance identity but the R5-A aggregation then read the **overwritten** `training_metrics.json`, extracting metrics from a different execution than the one the provenance describes.

## Cause of Re-Run

**Unidentified.** The re-run was not caused by the R5-A launch scripts (which write to `/mnt/storage_pool/liaoyuanjun/r5_a/`, not `r4_13scene_v2/`). The `r4_train_wrapper.py` writes only to its `--output` directory. The most likely explanations are:

1. The original R4 batch script had a retry/restart mechanism that re-ran candidate_c after the original run's checkpoint save failed (disk was 100% full at 3.5T).
2. A leftover process from the original R4 13-scene batch continued running and re-executed.

The R4 candidate_c processes for train/truck were still visible in `ps` at 00:06 on 09-19, 1.5+ hours after the original 22:46 start time — consistent with a run that completed 30K iterations, failed at checkpoint save, and was retried.

## Why the Numbers Differ

The original and re-run used the **same seed (0)**, **same config**, and **same camera_sequence** (verified). However, the skip mask computation (`compute_skip_mask.py`) involves floating-point sorting and threshold selection that is **not guaranteed deterministic** across CUDA/PyTorch executions. Two runs with identical inputs can produce:
- Slightly different skip masks → different suppressed gradients → different densification decisions → different final Gaussian counts (472,289 vs 476,167) → different PSNR (22.336 vs 22.379).

## Resolution: Which Artifact to Use

**The `final_results.json` (mtime 2026-09-18 23:58:04) is the authoritative R4 seed-0 artifact.**

Rationale:
1. It was generated from the **original** R4 run, which the `provenance.json` identifies.
2. It is the source of the published R4 report numbers (`r4-13scene-final.md`).
3. Its mtime (23:58) precedes the re-run (01:04), confirming it predates the overwrite.
4. The `sha256` hash of `final_results.json` is `ea645ac3a0f61f1b` (first 16 hex chars).

The current `training_metrics.json` in `r4_13scene_v2/{scene}/candidate_c/` is from the **re-run** and does NOT match the provenance. It should not be used as the R4 seed-0 source.

### Per-checkpoint data caveat

The `final_results.json` contains only the final 30K metrics, not per-checkpoint data. Per-checkpoint N_GS values for the R4 seed-0 candidate_c (needed for densification diagnostics) are only available from the re-run `training_metrics.json`. The densification diagnostics report qualifies these values accordingly.
